# Angular 17+ SSR Nginx Pitfall

**Extracted:** 2026-09-20
**Context:** During production deployment of Angular 17+ micro-frontends with SSR enabled.

## Problem
In Angular 17+, configuring a project for Server-Side Rendering (SSR) via `outputMode: "server"` generates a client fallback file named `index.csr.html` instead of `index.html`. 

If a multi-stage Dockerfile attempts to serve the browser build artifacts using a static Nginx container (e.g., `nginxinc/nginx-unprivileged`), Nginx will fail to find `index.html`. Consequently, the container will serve the default "Welcome to nginx!" page in production, completely masking the Angular application.

## Solution
To leverage Angular's native Hybrid SSR/CSR architecture, **do not use Nginx as the final stage**. Instead, use a Node.js base image and execute the Express server generated by Angular (`server.mjs`). This server natively handles SSR routing and automatically falls back to serving static files for CSR routes.

### Executable Code Block

```dockerfile
# Stage 1: Build
FROM node:24-alpine AS builder
WORKDIR /app
# ... build steps ...
RUN npm run build

# Stage 2: Production image with Node.js (Hybrid SSR/CSR)
# DO NOT USE nginxinc/nginx-unprivileged if using Angular SSR
FROM node:24-alpine AS production

WORKDIR /app

# Copy the dist folder containing both 'browser' and 'server' builds
COPY --from=builder /app/dist/your-app-name ./dist/your-app-name

# Expose port (e.g., for Cloudflare Tunnels or Reverse Proxies)
EXPOSE 8080
ENV PORT=8080
ENV NODE_ENV=production

# Execute the native Angular Express server
CMD ["node", "dist/your-app-name/server/server.mjs"]
```

## When to Use
- When deploying Angular 17+ SSR applications using Docker.
- When an Angular Docker container unexpectedly serves the "Welcome to nginx!" default page.
- When migrating an Angular SPA (served by Nginx) to an Angular SSR application.
